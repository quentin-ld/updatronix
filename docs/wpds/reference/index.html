Build Updatronix on the WordPress Design System

A reference for separating the legacy WordPress admin layer from the modern design system, choosing the right tokens and components, and moving Updatronix to a column-based shell with its sections in the dark navigation rail.

One project, three visual layers

Updatronix works on WordPressâ€™s update engine. Its interface currently borrows from three places at once: native wp-admin, a custom blue header, and a mix of WordPress components. The rework needs a single contract before any screen is redrawn.

The two systems

Legacy admin is not a theme of the new design system

They share a family resemblance because both are WordPress. Underneath, they are different contracts: different distribution, different tokens, different component APIs, and different assumptions about color and theming.

Do not blend the two

One surface belongs to one system. Do not put legacy admin blue on a WPDS component, do not skin WPDS controls with .button or .notice classes, and do not mix legacy and new tokens in the same component. If a legacy component is still required, isolate it and document why.

A note on versions

The npm packages and the WordPress runtime can move at different speeds. The versions used for this guide are @wordpress/theme 3.0.0, @wordpress/ui 0.25.0, @wordpress/components 43.0.0, @wordpress/dataviews 21.0.0, @wordpress/admin-ui 3.0.0, and @wordpress/icons 19.0.0. Check the WordPress version Updatronix supports before relying on a runtime API.

Separation rules

Six rules for every Updatronix screen

These are the non-negotiables for the rework. They are short on purpose: they should be checkable in review, not reinterpreted per screen.

1. One system per surface

A screen is either WPDS or legacy. There is no mixed mode inside a card, form, or table.

2. Tokens, never hex

Use --wpds-* for color, spacing, type, radius, and motion. A hardcoded value is a bug unless it is a documented brand asset.

3. One page header

Each screen has one page title, one short description, and one primary action. Breadcrumbs replace the old cross-links row.

4. Navigation lives in the rail

The eleven destinations are sidebar items in four groups. Nested tabs stay inside the page, not in a second horizontal bar.

5. One save model

One save model per surface, applied to every field. Updatronix uses manual save on Settings, Schedule, and Auto updates.

6. Native chrome stays native

The WordPress admin menu, footer, and global notices are outside the plugin surface. Do not restyle them.

Target structure in one sentence

A dark navigation column holds the eleven Updatronix destinations; the content frame holds one page header and one working surface, with tabs only where a page genuinely has sub-views.

The blue bar decision

The current header is a gradient sampled from the supplied screenshots: roughly #3549ac on the left, falling to #24242f on the right. It is decorative, not a token, and it competes with the WordPress admin menu for attention.

Remove it. Do not recolor it, shrink it, or turn it into a dark bar. Its functions move: the product identity and version move to the dark rail; Upgrade becomes a Pro item in the rail; the page title and description move into the page header. Documentation and Support get their own Help group in the rail instead of floating in the header.

Foundations Â· Color

Color is a role, not a hex value

The semantic tokens describe what a color is for. That is what makes theming and contrast auditing possible. Read the name before choosing the value.

A color token follows the pattern --wpds-color-<property>-<target>-<tone>[-<emphasis>][-<state>]. Take --wpds-color-background-interactive-brand-strong-active: it is a background for an interactive control, with brand tone, strong emphasis, in the active state.

Decoding the four role segments that matter most.
Segment Values What it answers
Property background, foreground, stroke Which CSS property is being set.
Target surface, interactive, content, track, thumb Whether it is a container, a control, static text, or a track-and-thumb part.
Tone neutral, brand, success, info, caution, warning, error The semantic intent. Caution is guidance; warning is action-needed; error is blocking.
Emphasis / state strong, weak / active, disabled How loud it is, and which interaction state it belongs to.

Foundations Â· Motion and cursor

Motion confirms a change, then gets out of the way

The system provides five durations and three easing intents. Use the shortest duration that still makes the change legible; never animate for decoration.

Durations

  • xs 50ms â€” transition offsets and micro-delays
  • sm 100ms â€” hover, focus ring, color changes
  • md 200ms â€” menus, popovers, standard transitions
  • lg 300ms â€” slides and reveals
  • xl 400ms â€” complex, multi-step transitions

Easings

  • subtle â€” near-imperceptible hover and color transitions
  • balanced â€” resizing, morphing, layout shifts
  • expressive â€” enter and exit for menus, popovers, dialogs, drawers

Hover and focus feedback belongs at sm. Opening a menu or a dialog belongs at md with expressive. A drawer or a large panel can use lg. Exits should be faster than entrances, generally 60â€“70% of the entrance duration.

Every non-essential transition must be wrapped in @media not (prefers-reduced-motion) or otherwise disabled when the user requests reduced motion. The tokens give you the values; the component still owns the behavior.

Cursor

--wpds-cursor-control defaults to pointer for buttons, checkboxes, and toggles. A desktop-style app can set cursor.control to default through the provider. Links keep the pointer regardless. Do not use a custom cursor to signal state; use the controlâ€™s visual state and focus ring.

Theme

ThemeProvider turns two seeds into the whole palette

You do not hand-pick a palette. You give the provider a primary and a background seed, and it generates ramps and semantic pairs that meet its contrast targets.

Application root 
import '@wordpress/theme/design-tokens.css';
import { ThemeProvider } from '@wordpress/theme';

export function App() {
  return (
    <ThemeProvider
      color={{ primary: '#3858e9', background: '#fcfcfc' }}
      cornerRadius="subtle"
      isRoot
    >
      <Admin />
    </ThemeProvider>
  );
}

The static stylesheet defines every default at :root. The provider adds per-subtree overrides on top. Inside WordPress admin and the editor, the stylesheet is registered as the wp-theme style handle; a plugin that renders its own app shell or iframe must enqueue it in that document instead of bundling a second copy.

Seeds, not palettes

Seeds are not guaranteed to appear unchanged

The ramp builder may adjust the seedâ€™s lightness to satisfy contrast. That is the point. Do not assert that the primary token equals the seed; assert the role and the contrast pair.

Nesting, portals, and iframes

  • Nest providers to theme a subtree. A dark sidebar can sit inside a light application, with its own background seed.
  • Tokens inherit through the CSS cascade, not the React tree. A portal outside the providerâ€™s DOM subtree will not inherit its overrides.
  • Use isRoot on the top-level provider so overlays portalled to the document pick up the overrides. Use at most one root provider per document.
  • An iframe needs the tokens stylesheet in its own <head> and the component styles registered in that document, usually through the experimental __experimentalStyleProvider from @wordpress/components.

Patterns Â· Destructive actions

Match the confirmation to the reversibility

Not every destructive action needs a red dialog. The design systemâ€™s decision tree asks two questions: does the action have an immediate visible result, and can it be undone?

No confirmation

No immediate visible result, or a standard undo exists. Use normal trigger styling and keep undo available.

Example: deleting a block in the editor.

Confirm dialog

Visible result but easily undone. Confirm, then show a snackbar (still from @wordpress/components) with Undo. The confirm button is primary, not destructive.

Example: moving a post to trash.

Irreversible AlertDialog

Permanent result. Use intent="irreversible" and no dismiss on escape or outside click. The primary button is destructive and names the object.

Example: deleting a log entry or a dependency chain.

Updatronix: deletion is permanent

Use an AlertDialog, not a confirm popover. Name the object and the consequence: â€œDelete log entryâ€ / â€œDelete permanentlyâ€, or â€œDelete chainâ€ / â€œDelete chainâ€. Do not make â€œDeleteâ€ the ambiguous default. After success, show a snackbar confirming what was removed.

Patterns Â· Error messages

What happened, why, and what now

An error is the only conversation a user has with the software when something breaks. It should turn a dead end into a next step.

1. What happened

State the outcome plainly. Name the specific item, not â€œsomethingâ€.

2. Why

Give the cause if it is known. If it is not, say so; do not invent a plausible reason.

3. What now

Offer at least one next step: a permission to fix, a format that works, a retry.

For Updatronix, an update failure belongs next to the log entry or in its details. A failed settings save belongs next to the field. A license activation failure belongs inline under the license key, with the reason and a link to the account page.

Patterns Â· Save and submit

Save once, from anywhere

Settings, Schedule, and Auto updates share one manual save model. Every change on a surface is staged until the primary â€œSave changesâ€ action commits it, so a radio or switch never quietly persists on its own.

Manual save

The right choice when changes are interdependent and saving has side effects, like rescheduling a cron event or changing what the next update run will install.

  • One primary â€œSave changesâ€ action per surface.
  • Toggles, radios, and text fields stage until save.
  • Guard against leaving with unsaved edits.

Sticky save bar

When the header action scrolls out of view, a compact bar appears at the top of the content area, repeating the surface title and â€œSave changesâ€.

  • Appears only after the header button leaves the viewport.
  • Runs the same action as the header, never a second save model.
  • Ctrl+S on Windows and Linux, âŒ˜S on macOS.

Auto updates is manual too

Turning auto-updates on does not install anything immediately. Core mode, translations, and each theme or plugin switch are saved together; the next scheduled check uses the new settings. A snackbar at the bottom of the screen confirms the save.

A switch still implies future effect, not instant effect. On Auto updates, make that timing explicit: the next check uses these settings after you save. Do not mix autosave and manual save on one surface.

Applied Â· Migration checklist

The review checklist for the applied screens

Each item is checkable without a design debate. If a screen fails one, it is not ready for the new shell.

  • The gradient header is gone, and no element reproduces it in another color.
  • Every working screen is a rail item; the screens hub is the index outside the rail, and the white secondary navigation column no longer exists.
  • Each screen has one page title, one description, and at most one primary action.
  • Every color, space, radius, and motion value in the product comes from a --wpds-* token.
  • The update log uses a DataViews table, not custom rows, for its primary view.
  • Irreversible actions use AlertDialog with intent="irreversible", name the object, and never use an ambiguous â€œDeleteâ€ label.
  • Health leads with readiness checks, then keeps each failure next to what happened, why, and what now.
  • One manual save per surface, kept in reach by a sticky bar and the Ctrl+S / âŒ˜S shortcut.
  • Focus rings, disabled states, and keyboard navigation are present on every control.
  • The wp-theme stylesheet is loaded once, and the provider is seeded for the admin color scheme.
  • Source strings are English; French ships as a translation, not as hardcoded copy.
  • @wordpress/ui and @wordpress/theme versions are pinned and tested against the target WordPress version.

Decisions reflected in the screens

Updatronix uses WordPress blue as the brand seed. Log details and export open in dialogs, not a drawer. The sticky save bar stays title plus action and disables the button when the surface is clean. Each was a product decision, not a token decision.
